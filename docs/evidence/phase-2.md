## 1. What was added

### `packages/types` — the two vocabularies

```ts
export const MARKET_GROUPS = ["us-equities", "china", "crypto", "pons"] as const;
export type MarketGroup = (typeof MARKET_GROUPS)[number];

export const LISTING_TIERS = ["tradeable", "quoted", "listed"] as const;
export type ListingTier = (typeof LISTING_TIERS)[number];

export const DISPLAY_ONLY_TIERS = ["quoted", "listed"] as const;
export function isMarketGroup(value: unknown): value is MarketGroup;
export function isListingTier(value: unknown): value is ListingTier;
export function tierNeedsFeed(tier: ListingTier): boolean;   // true only for "tradeable"
```

They are `const` tuples with a derived union type rather than enums, so the values exist at runtime for
validation and the type still rejects a typo at compile time. `tierNeedsFeed` is the single place that
decides which tier settles on chain, so config, the API and the web app cannot drift apart on it.

### `packages/contracts/deployments/robinhood_mainnet.markets.json` — the data

All **32** entries gained `"group": "us-equities"` and `"tier": "tradeable"`. The file's `note` now
states the tier rule and that only tradeable entries are listed on chain, so the rule travels with the
data. Nothing else in the file changed: the 32 symbols, tokens, feeds, leverage and maintenance values
are untouched.

The 32 are not a shortlist. `REFERENCE.md` Section 2 Finding 1 measured that only 33 of the 194
tokenized assets on this chain have a Chainlink feed at all, and `GLD` is the one unused.

### `packages/config/src/markets.ts` — the accessors

| Export                               | Behaviour                                                                                   |
| ------------------------------------ | ------------------------------------------------------------------------------------------- |
| `MarketListing`                      | One row of the deployment file. `feed` is optional, present if and only if the tier is tradeable |
| `marketsForChain(chainId)`           | The recorded list. An unrecorded chain throws                                                |
| `marketsForGroup(chainId, group)`    | The group's markets in file order. An **unknown** group throws; a known-but-empty one returns `[]` |
| `marketsForTier(chainId, tier)`      | The tier's markets, each re-checked against the invariant before it is handed back           |
| `marketForSymbol(chainId, symbol)`   | One market, or `undefined` — nothing invents a market                                        |
| `feedForSymbol(chainId, symbol)`     | The feed of a **tradeable** market. Throws for any other tier                                |
| `assertTierInvariant`, `validateMarkets` | The boundary itself, exported so callers and tests use the same check                    |

The market list is a generated literal in `src/markets.ts`, the same arrangement the contract addresses
above it already use, regenerated by **`pnpm --filter @hume/config sync:markets`**
(`packages/config/scripts/sync-markets.ts`, modelled on the existing `sync-deployments.ts`). The
deployment JSON stays the source of groups and tiers; a test fails if the generated copy ever drifts
from it, so the two cannot disagree silently. No group or tier is written as a literal anywhere in app
code.

`validateMarkets` runs at module load for both chains, so a mis-tagged row fails at import rather than
at the moment a price is read.

### `packages/contracts/script/AddMarketsMainnet.s.sol` — the same boundary on chain

The listing script now skips any entry whose tier is not exactly `tradeable`:

```solidity
if (!_isTradeable(list, p)) {
    console.log("skip", symbol, "not tier tradeable: display only, never listed on chain");
    return;
}
```

Without this, adding a quoted row to the market file would either revert on a zero feed address or, in
the worse case, open a leveraged market with no price source. An unknown tier is skipped too — opening a
market from a row nobody understands is the unsafe direction. An entry with no `tier` key at all is
treated as tradeable, so an older market file lists exactly as it did before.

## 2. The tier boundary, asserted in both directions

This is the acceptance condition, and the reason the phase exists: a Tier 2 price comes from DexScreener
or a reference price, and it must never be reachable through a field that settlement code reads.

**Direction 1 — a quoted or listed entry given a feed address fails:**

```
@hume/config: market UMC is tier "quoted" but carries feed 0xcdcd…cdcd;
a display-only tier must have no feed, or its price could reach settlement
```

**Direction 2 — a tradeable entry with no feed address fails:**

```
@hume/config: market NVDA is tier "tradeable" but has no feed address;
a tradeable market settles on chain and needs a price feed
```

Both directions are enforced in three independent places, so no single edit can bypass the rule:

| Enforced in                                 | When it fires                                             |
| -------------------------------------------- | --------------------------------------------------------- |
| `assertTierInvariant` / `validateMarkets`    | At module load and on every `marketsForTier` call          |
| `scripts/sync-markets.ts`                    | Before a bad row can even reach the generated literal      |
| `AddMarketsMainnet.s.sol` `_isTradeable`     | Before a non-tradeable row can be listed on chain          |

Proved against the real data rather than only against fixtures. Each probe edited the real market file,
ran the tooling, and was then reverted:

| Probe on `robinhood_mainnet.markets.json`              | Result                                            |
| ------------------------------------------------------ | -------------------------------------------------- |
| Removed `NVDA`'s feed, left it tier `tradeable`        | `sync:markets` exits 1; the config suite fails too |
| Changed `NVDA` to tier `quoted`, left its feed         | `sync:markets` exits 1                             |
| File restored                                          | 32 rows, `NVDA` tradeable with its feed, suite green |

A fourth test asserts the check is **not vacuous**: a valid row of each of the three tiers passes, and
every row of the real 32 passes in both directions.

## 4. One deviation from the phase text, and why

The phase's "Done when" line says `marketsForGroup(4663, "china")` returns the China set from the file.
It returns `[]`, because **Section 3.1 cut the China group to Phase 18** and this phase's own work item 4
says to tag all 32 as `us-equities`. The two lines in the plan disagree; the explicit instruction wins,
and the `china` group stays empty at launch.

So the test asserts what actually matters at this boundary: `china` is a **known** group that returns an
empty list, while a misspelled group throws. The research is not lost — `REFERENCE.md` Section 2
Finding 2 records that BABA and TSM are the two tradeable China names (both already in the 32, both
tagged `us-equities` today) and that UMC, FUTU, EWT and SIMO are quoted-only. Phase 18 regroups them by
editing the deployment file and running `sync:markets`; no code change is needed, which is the point of
keeping groups as data.

## 6. Finding for the operator: the protocol token still carries the retired brand

Found while reading `packages/config/src/deployments.ts`, and confirmed on chain at block `79379560`:

```
$ cast call 0xaf9eb3274b41e372c58b39fabd01e1d1eebc3579 "symbol()(string)"
"ALPHA"
$ cast call 0xaf9eb3274b41e372c58b39fabd01e1d1eebc3579 "name()(string)"
"Alpha Markets"
```

The comment in `deployments.ts` claimed this token's name was "Hume", checked on 2026-09-25. **That was
never true.** The comment is corrected; the recorded address and symbol are left as they are, because
they record what is on chain.

Why it matters, and why Phase 1 could not catch it:

- ERC-20 `name` and `symbol` are immutable here. **No rename is possible.**
- `scripts/check-brand.sh` greps the repository. This string arrives from the chain at runtime, so no
  repository check will ever see it.
- Any UI that shows the protocol token by reading it on chain would display the retired brand, which is
  exactly what Phase 1's scope forbids.

Three options, all cheap, and the choice is the operator's:

1. **Leave `BuybackModule`'s protocol token unset at launch.** Nothing reads the token, nothing displays
   it. Phase 17's gate does not require the buyback module to be live.
2. **Display the override.** `NEXT_PUBLIC_PROTOCOL_TOKEN_SYMBOL` already exists for this; the web app
   shows the configured symbol rather than the on-chain one. The on-chain name stays wrong for anyone
   looking at the explorer.
3. **Deploy a fresh token** with the right name and point `setProtocolToken` at it. Costs gas only, which
   Section 0.2 shows there is plenty of, but it abandons the 1,000,000,000 existing supply.

Recorded here rather than acted on: it is a product decision, not a Phase 2 code change.

**Cost of this phase: $0, apart from three `eth_call` reads.**
